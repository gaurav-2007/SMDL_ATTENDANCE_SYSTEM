TASK 1: ACADEMIC API AUTHORIZATION
--------------------------------------------------------------------------------
- File: server/src/routes/academicRoutes.js
- Identified Risk: Broken Object-Level Authorization (BOLA). Any authenticated
  user—including students and unapproved accounts—could create, alter, or delete
  courses, divisions, subjects, and timetables via direct API calls.
- Remediation Implemented:
  * Imported { restrictTo, restrictToActiveOnly } from '../middleware/roles'.
  * Locked down all mutation endpoints strictly to 'admin':
      POST   /api/academic/courses                   -> admin only
      DELETE /api/academic/courses/:id               -> admin only
      POST   /api/academic/divisions                 -> admin only
      DELETE /api/academic/divisions/:id             -> admin only
      POST   /api/academic/subjects                  -> admin only
      POST   /api/academic/subjects/batch            -> admin only
      DELETE /api/academic/subjects/:id              -> admin only
      POST   /api/academic/timetable                 -> admin only
      DELETE /api/academic/timetable/:id             -> admin only
      POST   /api/academic/timetable/load-smdl-matrix -> admin only
  * Read endpoints (GET /courses, GET /divisions, GET /subjects, GET /teachers-list,
    GET /timetable/:division_id) remain accessible to authenticated students and
    teachers for class schedules and attendance selection.


TASK 2: ANNOUNCEMENT OWNERSHIP AUTHORIZATION
--------------------------------------------------------------------------------
- File: server/src/controllers/announcementController.js
- Identified Risk: Insecure direct object deletion and silent PostgREST query
  filtering. Previously, calling .delete().eq('sent_by', req.user.id) returned
  { error: null } with 0 rows deleted if unauthorized, giving misleading 200 OK
  responses without verifying ownership, or allowing horizontal privilege attacks.
- Remediation Implemented:
  * Implemented explicit pre-deletion fetch of announcement record.
  * Verified existence: returns HTTP 404 if record does not exist.
  * Enforced authorization rule:
      if (req.user.role !== 'admin' && announcement.sent_by !== req.user.id) {
        res.status(403);
        throw new Error('Not authorized to delete this announcement.');
      }
  * Admin retains global administrative deletion capability.
  * Teachers can ONLY delete announcements they authored.
  * Attached documents in announcement_attachments are automatically cleaned up.
  * Verified that announcement update endpoints do not exist (only GET, POST, DELETE).


TASK 3: PERSISTENT OTP STORAGE & PRODUCTION HARDENING
--------------------------------------------------------------------------------
- Files:
    server/src/services/otpService.js
    server/src/controllers/authController.js
    server/supabase/migrations/006_email_verifications.sql
- Identified Risk: Pending OTPs were previously stored in an in-memory Map() and
  bypassed the database email_verifications table. Additionally, local file-based
  persistence had to be strictly forbidden in production.
- Remediation Implemented:
  * PostgreSQL/Supabase email_verifications table is the SOLE and ONLY source
    of truth for OTP state in production.
  * Completely removed .local_otp_store.json from production. No local files are
    ever created, written, or read for OTP storage.
  * Fail-Safe Error Handling: If the database is unavailable in production, the
    service fails safely with an explicit error ("Verification service temporarily
    unavailable. Please try again later."). It NEVER silently falls back to local storage.
  * Generation: Cryptographically secure 6-digit numeric OTP via crypto.randomInt(100000, 1000000).
  * Expiry: Strict 10-minute lifetime (expires_at).
  * Single-Use: Invalidation upon verification and consumed_at tracking.
  * Attempt Limiting: Locked out after 5 incorrect attempts (MAX_ATTEMPTS = 5).
  * Resend Cooldown: 45-second lock between OTP requests to prevent SMTP spamming.
  * Production Masking: OTPs are strictly suppressed from server logs and API responses
    in production/staging environments.
  * Tamper-Proof Verification Token: Issues HMAC-SHA256 token (id.timestamp.signature)
    tied to the user's verified session for student and teacher registration.
  * Development-Only Behavior: Ephemeral in-memory fallback is strictly restricted
    to NODE_ENV === 'development' and completely disabled in staging/production.


TASK 4: TEACHER APPROVAL & REJECTION NOTIFICATIONS
--------------------------------------------------------------------------------
- Files:
    server/src/services/emailService.js
    server/src/controllers/adminController.js
- Identified Risk: When administrators approved or rejected a teacher's account,
  no email was dispatched. Applicants were unaware of account status changes.
- Remediation Implemented:
  * Created sendTeacherApprovalEmail(toEmail, teacherName):
      - Official SMDL College branded responsive HTML template.
      - Informs teacher of account activation and access to faculty tools.
      - Includes direct "Access Faculty Dashboard" button pointing to CLIENT_URL.
      - Outlines faculty security protocols and assigned division guidance.
  * Created sendTeacherRejectionEmail(toEmail, teacherName, rejectionReason):
      - Formal, professional rejection notice detailing the administrative reason.
      - Provides administrative support email and contact guidance.
  * Integrated hooks into approveTeacher and rejectTeacher in adminController.js.
  * Maintained strict approval workflow:
      Registration -> Email Verification -> PENDING -> Admin Approval -> ACTIVE.
  * Rejected teachers are permanently barred from accessing faculty routes.


TASK 5: ATTENDANCE API RATE LIMITING
--------------------------------------------------------------------------------
- Files:
    server/src/config/env.js
    server/src/middleware/rateLimiter.js
    server/src/routes/attendanceRoutes.js
- Identified Risk: POST /api/attendance/mark lacked route-specific rate limiting,
  leaving it vulnerable to automated attendance brute-force, burst photo submissions,
  and server resource exhaustion.
- Remediation Implemented:
  * Added configurable environment variables:
      ATTENDANCE_LIMIT_WINDOW_MS (default: 60000 ms / 1 minute)
      ATTENDANCE_LIMIT_MAX (default: 10 requests per minute)
  * Implemented attendanceMarkLimiter in rateLimiter.js using express-rate-limit v8.
  * Keyed per authenticated student: req.user.id ? `user_${req.user.id}` : req.ip.
    This prevents campus Wi-Fi or classroom hotspot shared IPs from blocking
    multiple students.
  * Configured validate: { keyGeneratorIpFallback: false } for IPv6 safety.
  * Mounted specifically on POST /api/attendance/mark.
  * Preserved full functionality for location verification, selfie uploads, and
    teacher manual override flows (POST /api/attendance/override).

4. DATABASE CHANGES & MIGRATIONS
================================================================================
Migration File:
  server/supabase/migrations/006_email_verifications.sql

Schema Definition:
  CREATE TABLE IF NOT EXISTS public.email_verifications (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(255) NOT NULL,
    otp_code VARCHAR(10) NOT NULL,
    role VARCHAR(20) NOT NULL DEFAULT 'student',
    is_verified BOOLEAN DEFAULT false,
    attempts INT DEFAULT 0,
    expires_at TIMESTAMPTZ NOT NULL,
    verified_at TIMESTAMPTZ,
    otp_token VARCHAR(255),
    consumed_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ DEFAULT now()
  );

Indices Created:
  - idx_email_verifications_email_verified ON email_verifications(email, is_verified);
  - idx_email_verifications_token ON email_verifications(otp_token);

Database Safety Guarantee:
  - No existing student, teacher, user, lecture, or attendance test records
    were altered or deleted.
