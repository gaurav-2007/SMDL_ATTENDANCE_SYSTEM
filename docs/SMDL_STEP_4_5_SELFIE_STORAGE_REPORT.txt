1. EXISTING SELFIE ARCHITECTURE (PRIOR TO STEP 4.5)
--------------------------------------------------------------------------------
Prior to Step 4.5, student attendance marking via webcam captured client-side
images as Base64 Data URLs (`data:image/jpeg;base64,...`). The backend stored
the raw, uncompressed Base64 text directly into the `attendance.selfie_url` text
column in PostgreSQL.

Existing records identified during the database audit:
- 4 legacy attendance records in the database contained raw Base64 data URIs.
- High database bloat (~50 KB to ~200 KB per row stored directly in relational tables).
- No automatic retention or TTL: selfie records remained indefinitely.
- Attendance queries loaded heavy Base64 strings across network payloads.

--------------------------------------------------------------------------------
2. PROBLEM IDENTIFIED
--------------------------------------------------------------------------------
- Storage Inefficiency: Storing image binaries directly in PostgreSQL tables causes
  table bloat, high I/O latency, slow index traversal, and degraded query throughput.
- Privacy & Compliance Risk: Retaining biometric facial verification photographs
  indefinitely without a retention schedule poses severe data privacy compliance risks.
- Lack of Signed URLs: Base64 strings were returned raw to API clients without access
  control or expiry semantics.

3. NEW STORAGE ARCHITECTURE
--------------------------------------------------------------------------------
Architecture Diagram:

  Student Web Camera
          │
          ▼ (POST /api/attendance/mark with Base64 payload)
  Backend Attendance API
     ├─► Server-Side Validation (magic bytes: JPEG/PNG/WebP, min 10B, max 5MB)
     ├─► Upload to Supabase Storage (Private Bucket: attendance-selfies)
     │       Path: attendance-selfies/{studentId}/{attendanceId}.jpg
     ├─► Store canonical storage path in PostgreSQL (Zero Base64 in new rows)
     │       selfie_url = 'attendance-selfies/{studentId}/{attendanceId}.jpg'
     └─► Compensation Rollback: If DB insert fails, uploaded storage object is
         immediately deleted via compensation hook to prevent orphan objects.

  Access & Display:
     ├─► Authorized Faculty / Admin / Student Self requests attendance selfie
     └─► Backend generates short-lived Supabase Signed URL (15-30 min expiry)

  48-Hour Retention Lifecycle:
     ├─► Expiration timestamp: UTC marked_at + 48 Hours
     ├─► Hourly Server-Side Cleanup Job (0 * * * *)
     │       Identifies records where marked_at + 48h <= NOW() UTC
     │       Deletes physical storage object from bucket
     │       Clears database reference (`selfie_url = null`)
     │       Preserves attendance row, status ('PRESENT'), marked_at, student_id
     └─► Audit Logs & Historical Attendance remain 100% intact.

8. 48-HOUR RETENTION IMPLEMENTATION
--------------------------------------------------------------------------------
- Retention Duration: Configurable via `ATTENDANCE_SELFIE_RETENTION_HOURS=48` (Default: 48).
- Computation: Server/PostgreSQL UTC timestamp calculation:
    `selfie_expires_at = selfie_uploaded_at + INTERVAL '48 hours'`
- Timezone Agnostic: Operates on absolute UTC timestamps; never dependent on
  browser local clock or client time manipulation.
- Backend Restart Resilience: Expiration state is fully persisted in PostgreSQL;
  survives server crashes and restarts without state loss.

--------------------------------------------------------------------------------
9. CLEANUP SCHEDULER IMPLEMENTATION
--------------------------------------------------------------------------------
Module: server/src/services/selfieCleanupJob.js
Scheduler: node-cron (`0 * * * *` — hourly at minute 0)
Lifecycle Hook: Initialized on backend startup (`index.js -> initSelfieCleanupJob()`)
Workflow:
  1. Queries expired attendance records (`selfie_expires_at <= NOW()` or `marked_at <= NOW() - 48h`).
  2. For each expired record:
     a. Attempts object removal from `attendance-selfies` bucket.
     b. If deletion succeeds, updates database: `selfie_url = null`.
     c. If object was already missing, handles idempotently: updates `selfie_url = null`.
     d. If storage deletion fails, logs failure and leaves DB reference for next retry.
  3. Preserves `attendance.id`, `attendance.status`, `attendance.lecture_id`, `attendance.student_id`.

--------------------------------------------------------------------------------
10. FAILURE / RETRY BEHAVIOR
--------------------------------------------------------------------------------
- Upload Failure:
    * If Supabase Storage upload fails, attendance marking is aborted.
    * Rejects request with HTTP 500 / clear recoverable error message.
    * No false attendance record is inserted into PostgreSQL.
- Database Failure after Successful Upload:
    * Compensation rollback immediately calls `deleteSelfieObject(storagePath)`
      to delete the newly uploaded storage object.
    * Prevents orphan files from accumulating in storage.
- Missing Storage Object during Cleanup:
    * Reconciles safely without throwing or crashing.
    * Clears DB pointer and logs `Already missing: 1`.
- Concurrency & Idempotency:
    * Cleanup mutex guard (`isCleanupRunning`) prevents concurrent tick collisions.
    * Multiple worker calls exit safely with `{ skipped: true }`.
