4. VERIFICATION OF THE 7 CRITICAL REQUIREMENTS
================================================================================

--------------------------------------------------------------------------------
VERIFICATION 1: Attendance records cannot be duplicated incorrectly (VERIFIED)
--------------------------------------------------------------------------------
- Database Constraint:
  Table 'attendance' has a database-level composite unique constraint:
  UNIQUE(lecture_id, student_id).
- Application Layer:
  attendanceController.js executes a SELECT check before attempting insert.
  If existing attendance is detected, HTTP 400 is returned immediately.
- Concurrency Safety:
  If concurrent requests bypass the read check simultaneously, PostgreSQL's
  atomic index insertion rejects the duplicate with error code 23505 (unique_violation).
- Secondary Schema:
  Table 'attendance_records' similarly enforces UNIQUE(timetable_id, attendance_date, student_id).
- Live Database Inspection:
  0 duplicate attendance records found in the database.

--------------------------------------------------------------------------------
VERIFICATION 2: Notification deduplication is safe (VERIFIED)
--------------------------------------------------------------------------------
- Architecture:
  In-app notifications are written database-first to the 'notifications' table.
- Deduplication Strategy:
  Deduplication is enforced at the producer domain layer:
  * Lecture reminders are gated by lecture_notification_logs (event_key UNIQUE).
  * Low-attendance alerts are gated by low_attendance_warnings (weekly UNIQUE).
  * Attendance notifications fire strictly upon successful attendance insertion.
  * Announcement notifications fire strictly on new announcement insertion.
- Live Database Inspection:
  No unconstrained duplicate notification loops found.

--------------------------------------------------------------------------------
VERIFICATION 3: Lecture reminder deduplication is atomic (VERIFIED)
--------------------------------------------------------------------------------
- Database Anchor:
  Table 'lecture_notification_logs' with event_key VARCHAR(120) UNIQUE NOT NULL.
- Mechanism in lectureScheduler.js:
  eventKey = START_${lecture.id}_${todayStr}
  An atomic SQL INSERT is executed:
  INSERT INTO lecture_notification_logs (event_key, ...)
  If successful -> Claimed! Proceed with notifications.
  If error code 23505 -> Already claimed by another worker! Abort immediately.
- Reschedules & Cancellations:
  Cancellations use event key: CANCEL_${lectureId}_${Date.now()}
  Reschedules use event key:   RESCHED_${lectureId}_${newTime}_${Date.now()}
  Legitimate multiple schedule modifications are never suppressed by start reminders.

--------------------------------------------------------------------------------
VERIFICATION 4: Low-attendance warnings have proper deduplication (VERIFIED)
--------------------------------------------------------------------------------
- Database Anchor:
  Table 'low_attendance_warnings' with composite constraint:
  UNIQUE(student_id, subject_id, warning_period_start).
- Deduplication Window:
  warning_period_start is calculated as the Monday date of the current calendar week.
- Mechanism in attendanceNotificationService.js:
  An atomic SQL INSERT is executed for (student_id, subject_id, weekMonday).
  First evaluation of the week succeeds and sends the warning.
  Subsequent evaluations during the same calendar week hit error 23505 and abort,
  preventing duplicate spam across classes.
  The following Monday date rolls over, allowing a fresh warning if still below threshold.

VERIFICATION 6: Storage references are valid (ACTION REQUIRED)
--------------------------------------------------------------------------------
- Storage Buckets:
  supabaseAdmin.storage.listBuckets() returned []. NO buckets exist in Supabase.
- Current Attendance Selfies:
  The 4 attendance rows in 'attendance' store webcam photos as raw Base64 strings:
  'data:image/jpeg;base64,/9j/4AA...' (15 KB to 42 KB per row).
- Announcement Attachments:
  0 files currently attached.
- Production Risk:
  Storing raw Base64 in PostgreSQL causes database bloat and query latency.
  At college scale (500 students x 4 lectures = 2000 images/day = 60 MB/day),
  the database will hit the Supabase 500 MB limit in under 2 weeks.
- Required Action:
  Create the 'attendance-selfies' bucket in Supabase Storage and upload files
  via storage API, storing only the public/signed CDN URL in the database.

- Backend Security Boundary:
  The Node.js Express API connects using service_role, while user identity and
